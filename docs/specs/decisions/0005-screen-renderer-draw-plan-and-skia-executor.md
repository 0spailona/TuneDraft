# ADR-0005: Draw plan and Skia executor for the screen renderer

## Status

Accepted

## Context

The screen renderer (roadmap stage 4) must turn the layout engine's character-unit output ([ADR-0004](0004-layout-character-units-and-wrap-policy.md)) into pixels without breaking the rules the specs already fixed. Rendering owns drawing only — it computes no geometry of its own (№14) — yet four concrete choices had to be made before code could exist. First, *where the last conversion lives*: the engine emits character units, a renderer draws pixels; multiplying by the monospace advance at draw time ([ADR-0004](0004-layout-character-units-and-wrap-policy.md)) still leaves open which component multiplies, and where the one piece of geometry rendering *is* allowed to own — wrapping text lines in a proportional font (№6, [ADR-0004](0004-layout-character-units-and-wrap-policy.md) item 4) — belongs. Doing either inside the Skia call sites would scatter geometry knowledge across draw calls and make the pipeline untestable without Skia.

Second, *which text carries which font*. №32 fixes monospace for fret digits; №24 requires column texts to ride under their column, and №6 text lines to flow like prose.

Third, the bass clef 𝄢 (№36). U+1D122 is absent from Android system fonts, so no text-drawing approach can render it.

Fourth, vertical metrics. [ADR-0004](0004-layout-character-units-and-wrap-policy.md) postponed the provisional vertical metrics (`ROW_SPACING_CHARS`, `TEXT_ROW_SPACING_CHARS`) to stage 4, where the theme fixes them. Fifth, page margins (№7, №23): the engine emits geometry relative to the system strip — where that strip sits inside the document width, and how much air the document gets above the first ribbon row, were still open; the decision below fixes both as renderer-owned placement.

## Decision

1. **A deterministic draw plan between the layout and the executor.** `src/infrastructure/rendering/plan.ts` translates the engine's character-unit dictionary into px primitives (`stringLine`, `fretDigit`, `barline`, `columnText`, `clef`, `textRow`) by multiplying by `advancePx` — the measured advance of the monospace fret-digit font (№32, [ADR-0004](0004-layout-character-units-and-wrap-policy.md) item 1). The plan is a pure, deterministic function of `(model, layout, options)`: same inputs → identical plan (№14, pinned by `plan.test.ts`). The executor (`skia.ts`) contains no geometry: it dispatches on `primitive.kind` and draws. `NotebookCanvas.tsx` holds no arithmetic of its own: `floor(widthPx / advance)` → `layoutNotebook` → plan → picture. Only one piece of geometry enters rendering: `wrapTextLine` wraps text lines in the proportional theme font (№6) through an injected `TextLineMeasurer` — the measurer stays an interface, so the plan never imports a framework (R1) and tests substitute a deterministic fake (№34).

2. **Fonts by role, per the theme (№32).** `theme.ts` — the single hardcoded MVP theme — fixes three roles: fret digits and column texts in the monospace family (fret digits at 16, column texts at 12 with `includeFontPadding: false`), text lines in the proportional `sans-serif` family at 18/36 (№6, №24, №32). Skia's `matchFont` resolves the platform typeface per family at render time; no font files ship. The advance of `fonts.fretDigits`, measured on the glyph «0» by `measureMonoAdvancePx`, *is* the character unit of the whole geometry pipeline (№32, [ADR-0004](0004-layout-character-units-and-wrap-policy.md) item 1).

3. **The bass clef is a built-in Skia path, not a glyph.** `skia.ts` draws 𝄢 (№36) as a path — head circle plus a two-curve "comma" stroke and two F dots — in normalized fractions of the clef rectangle the plan emits (`clef.xPx/yPx/widthPx/heightPx` come from the plan; the path defines no geometry of its own). No dependency on the system font stack, which lacks U+1D122.

4. **Vertical metrics are final.** `ROW_SPACING_CHARS = 2` and `TEXT_ROW_SPACING_CHARS = 2` (`src/domain/layout-engine/config.ts`) are confirmed as the theme's final vertical metrics (№32): column texts stack at 2 engine characters per row (№24), and a system strip closes with that same 2-character gap, so stacked texts never collide with the next system. `TEXT_ROW_SPACING_CHARS` was revised from the provisional 1 to 2 after the on-device check: a character is the *advance* of the mono fret-digit font (~9.6px at size 16), which is smaller than the *height* of the 12px column text and the 18px text-line glyphs the same unit must vertically separate — one advance left less clearance than a glyph's ascent, so texts collided with strings and the next system's digits protruded into text lines. `theme.fonts.textLine.lineHeight` was raised accordingly (25 → 36) so a text line's budget clears the ~9.3px upward protrusion of the next system's digits.

   Additionally, text lines carry a **vertical padding** (`theme.textLinePaddingPx`, 12px): the plan lowers the first wrapped row by the padding from the text line's top and adds it to the block height on both ends (`rows · lineHeight + 2 · padding`, pinned by `plan.test.ts`). Before the padding, the text-line block height exactly matched the glyph span, so the first/last wrapped rows butted right against the string lines of neighboring tab lines; the padding separates glyphs from strings on both ends without touching the wrap budget (lineHeight) or the engine's character-unit geometry (ADR-0004).

5. **Any whitespace run is a word separator in text-line wrapping.** `wrapTextLine` splits on `/\s+/`: newlines and tabs inside a `TextLine.text` collapse to plain spaces — in the MVP a text line renders as one flowing paragraph (№6, pinned by `plan.test.ts`). The model's "multi-line text" wording (№6) is interpreted as *unlimited free text*, not as preserved line structure; no raw `\n`/`\t` ever reaches `drawText` (a glyphless control character would render as tofu or nothing). Preserving hard line breaks is deferred until the text-input stage (stage 5) shows a need for it; until then, `wrapTextLine` is the single place that decides this policy.

6. **The document is one centered block with a fixed top margin (№7, №23).** The plan owns two placement values beyond character-unit translation. First, **horizontal centering**: `leftOffsetPx = max(0, (widthPx − (leftMarginPx + stripChars · advancePx)) / 2)` — one single offset, computed from the *first* tab system's strip width (`widthChars` is fixed in MEASURE, №20, so every system shares it), applied identically to every system of every tab line: the whole tab block («отступ под ключ + полоса» — clef margin plus strip) rides as one unit centered in `widthPx`, so left and right document margins come out equal for systems within their strip (an overflowing measure extends past it, [ADR-0004](0004-layout-character-units-and-wrap-policy.md) item 3; the demo symmetry is pinned exactly by `plan.test.ts`). `max(0, …)` clamps documents narrower than the block to the left edge — no negative offset ever reaches a primitive. All left-x arithmetic adds this offset exactly once (strings/digits/barlines/column texts at `leftOffsetPx + leftMarginPx + …`, clef at `leftOffsetPx`). Second, **the document top margin**: `theme.documentTopPaddingPx` (32 px) — the vertical gap between the document top and the first ribbon row (№7: «как бумажная тетрадь», №23: below the status bar); `yCursorPx` starts there, and `heightPx` includes it exactly once (`heightPx = documentTopPaddingPx + Σ row heights`, pinned by `plan.test.ts`). The margins of the "paper" belong to the renderer, not the engine (№23): the engine's character-unit geometry stays width-relative, and the plan is the single place that converts it into document coordinates. Wrapped text rows are not part of the tab block: each wrapped row centers on its *own measured width* over the full `widthPx` (№7 prose centering), never offset by the tab-block shift; a row wider than the document (overflow, [ADR-0004](0004-layout-character-units-and-wrap-policy.md) item 3) clamps to x = 0.

## Consequences

**Positive**

- The screen pipeline is testable without Skia: `plan.test.ts` (a–h) pins determinism, fret-digit placement, barlines, column-text stacks, text-line wrapping, the draw window, clef margins, and the centered-block/top-margin geometry (decision 6) with a fake measurer (№34); the executor stays thin enough that its correctness is a code-review concern, not a test-suite one.
- Screen and PDF agreement survives by construction (№14, №23): the HTML→PDF exporter (stage 8) consumes the same plan — including the page-margin placement of decision 6, so screen and export agree on `leftOffsetPx` / `documentTopPaddingPx` automatically.
- The clef renders everywhere Android renders, independent of font availability.
- The draw window (№28) already works at the plan level — `window` slices primitives while `heightPx` keeps the full document height for scroll sizing — though stage-4 wiring draws the whole ribbon and leaves windowed drawing to stage 6.
- Centering is a pure arithmetic on `(widthPx, advance, strip)` — it re-runs on rotation together with the layout rebuild (№23) and cannot disagree between systems, because the offset is computed once per document.

**Negative**

- The plan reads the model (kind of columns, notes, texts) alongside the layout, so the "layout is the only geometry source" rule is nuanced: the model remains the source of *semantics* (№19), the layout of *coordinates*. Two vocabularies must stay in sync by test (`plan.test.ts`).
- Proportional wrapping depends on the platform typeface `matchFont` resolves; a different platform font changes wrap points. Determinism holds per-platform (same platform → same plan), not across platforms.
- The path-based clef is a stylized simplification of the musical glyph — acceptable for the notebook look (№36), not a font-accurate 𝄢.

## Alternatives Considered

- **Skia declarative elements directly from layout values** — rejected: `<Canvas>` children are elements, not callbacks; per-primitive JSX would re-run layout-to-JSX conversion on every render and scatter the multiply-by-advance across call sites, breaking determinism review (№14).
- **Imperative `Skia.Canvas` with draw callbacks** — rejected: 2.x `<Canvas>` is declarative; `PictureRecorder → SkPicture → <Picture>` is the supported imperative recording bridge, and the recorded picture is replayable by the PDF/preview renderers of stages 6–8.
- **Embedding the clef as a font file (custom typeface)** — rejected: shipping a font for one glyph adds an asset pipeline for what a few path commands draw; a missing-glyph fallback in system fonts would degrade silently to a tofu box.
- **Layout engine wraps text lines (move `wrapTextLine` into the kernel)** — rejected in [ADR-0004](0004-layout-character-units-and-wrap-policy.md) already: the engine would need proportional-font metrics, exactly the knowledge character units exist to keep out of the kernel (R1).
- **Column texts in the proportional family at column text size** — rejected: №24 rides texts under columns whose grid is character-based; the same monospace family keeps the stack step at exactly 1 engine character (№32), which a proportional family cannot guarantee.
