# План: формализация КАРТЫ-ПРОЕКТА в спек-систему

> Дата: 2026-09-17
> Основание: [docs/КАРТА-ПРОЕКТА.md](docs/КАРТА-ПРОЕКТА.md) — решения №1–№40, архитектура, дорожная карта 0–10
> Куда: `docs/specs/` — спек-система, развёрнутая до кода ([ADR-0001](docs/specs/decisions/0001-bootstrap-spec-system-before-code.md), [ADR-0002](docs/specs/decisions/0002-specs-live-in-docs-specs.md))
> Инструмент: процедура `vibespec-create` (создание доменных спеков по шаблонам из META.md)

---

## Контекст

Спек-система уже существует: META.md / WORKFLOW.md / INDEX.md, архитектурные спеки
(layers.md, data-flow.md), шаблоны контрактов и ADR, ADR-0001/0002. В `domains/` лежит
единственный `placeholder-domain/` — экземпляр формата, который **подлежит удалению** при
создании первого реального домена. Проект — pre-code: каждого утверждения о коде, которого
ещё нет, обязан сопровождать маркер `<!-- TODO: verify -->` (протокол ADR-0001).

Задача: превратить 40 решений КАРТЫ в структурированные доменные спеки, на которые смогут
опираться агенты при написании первого кода (этапы 1–2 дорожной карты).

## Язык документов

Существующие 10 файлов спек-системы написаны на английском — новые доменные спеки пишутся
также на английском для единообразия системы. Русский остаётся языком интерфейса
приложения (№31) и документов планирования (КАРТА, этот план). Ссылки на решения КАРТЫ
даются в форме `(№NN)`.

## Структура доменов

Шесть доменов выводятся из архитектуры КАРТА §2 (модель → layout → рендер; ввод; хранение; оболочка):

```
domains/
├── tabulature/            README.md + notebook-model.md      — чистая модель данных
├── layout-engine.md       (однофайловый домен)               — геометрия: колонки → координаты
├── editing/               README.md + cell-and-column-menus.md + lines-and-gestures.md
├── app-shell.md           (однофайловый домен)               — навигация, режимы, тулбар
├── storage/               README.md + pocket.md + library.md  — файлы, карман, библиотека
└── rendering/             README.md + pdf-export.md           — Skia-экран + HTML→PDF
```

## Шаги плана

### Шаг 1 — Домен `tabulature` (ядро модели)

Создать `domains/tabulature/README.md` (шаблон Domain README, все 9 секций) и
`domains/tabulature/notebook-model.md` (шаблон Domain Detail).

Содержание — из решений №1–№4, №6, №18–№22: тетрадь с полем `version`; строки ленты двух
видов (таб / текст); **колонка как сущность**, объединяющая ячейки четырёх струн; ноты —
цифры ладов 0–24; колонка-черта (запрещена при нотах, без текстов); тексты колонки ≤ 3
привязаны по `columnId`; стабильные `id` и каскадные удаления; струны как список MIDI-нот
(расширяемо до 5-й); поле `duration` с первого дня; `albumId` с первого дня.

**Критерии приёмки:** все секции шаблонов на месте в порядке META.md; утверждения о
несуществующем коде несут `<!-- TODO: verify -->`; Key Files / Core Types = «None yet» +
TODO; ссылки `(№NN)` соответствуют КАРТЕ; перекрёстные ссылки относительные от
`docs/specs/` и ведут на существующие файлы.

### Шаг 2 — Домен `layout-engine` (однофайловый)

Создать `domains/layout-engine.md` по шаблону Domain README (однофайловые домены —
`domains/<name>.md`).

Содержание — из решений №14, №20, №23, №24, №28: чистый JS-движок геометрии; ширина
колонки минимум 4 символа / максимум 12 с раздвижением под текст; ёмкость таб-строки ≈
85% ширины экрана / минимальная ячейка; правила переноса (сначала убираются пустые колонки
в конце, затем новая строка и перенос хвоста); такт не разрывается между системами;
пересчёт переноса при повороте экрана; PDF и превью считаются по своей ширине.

**Критерии приёмки:** 9 секций по порядку; TODO-маркеры; ссылки `(№NN)`; валидные ссылки.

### Шаг 3 — Домен `editing`

Создать `domains/editing/README.md` + `cell-and-column-menus.md` + `lines-and-gestures.md`
(шаблон Domain Detail).

Содержание — из решений №5, №11, №21, №25, №35, №36, №37, №40: тап → выделение
ячейки/колонки; меню в нижней панели; панель ладов 0–24 (+ черта для пустой ячейки; правка
— без черты); операции меню колонки (вставить слева/справа, очистить, удалить каскадом,
добавить текст с запретом при 3); управление строками (кнопка «+», лонг-тап по пустому
месту → текст-строка, drag строк, ручка 𝄢 + корзина, удаление такта/строки
распространением выделения); undo/redo ≤ 3 на любую мутацию модели; режимы правки/чтения.

**Критерии приёмки:** README + 2 detail-файла, секции по порядку; TODO-маркеры; `(№NN)`;
валидные ссылки.

### Шаг 4 — Домен `app-shell` (однофайловый)

Создать `domains/app-shell.md` по шаблону Domain README.

Содержание — из решений №11, №23, №28, №31, №32, №37, №39, №40: библиотека — стартовый
экран; системный «Назад» (в редакторе = «Закрыть» с переспросом, в библиотеке = выход);
переключатель «Править»/«Чтение»; тулбар (Сохранить, Закрыть, Undo, Redo, Экспорт PDF);
виртуализация — окно рендера вокруг экрана; обе ориентации с пересчётом переноса; minSdk
24; i18n — русский базовый, строки через словарь; в MVP одна зашитая тема.

**Критерии приёмки:** 9 секций по порядку; TODO-маркеры; `(№NN)`; валидные ссылки.

### Шаг 5 — Домен `storage`

Создать `domains/storage/README.md` + `pocket.md` + `library.md` (шаблон Domain Detail).

Содержание — из решений №26, №29, №30, №38: файл `tet-<id>.json` создаётся при первом
«Сохранить»; видимое имя — внутри JSON; карман — один на приложение, пишется после каждого
действия; переспрос при запуске (да → в постоянную + чистим / нет → чистим); явный отказ
при закрытии чистит карман сразу; восстановление пересоздаёт удалённый файл; AsyncStorage —
настройки; библиотека: карточки (имя + превью `tet-<id>.png`, рендер при «Сохранить»),
сортировка по дате изменения, битый JSON → карточка «повреждена», контекстное меню
(переименовать/удалить/экспорт JSON рядом с .apk); запрос имени при создании + шаблон
новой тетради №38; альбомы после MVP, но `albumId` с первого дня.

**Критерии приёмки:** README + 2 detail-файла, секции по порядку; TODO-маркеры; `(№NN)`;
валидные ссылки.

### Шаг 6 — Домен `rendering`

Создать `domains/rendering/README.md` + `pdf-export.md` (шаблон Domain Detail).

Содержание — из решений №7, №8, №14, №33, №30 (превью): рендерер Skia для экрана;
HTML→PDF через expo-print + expo-sharing; оба потребляют выход layout-движка; A4 портрет;
заголовок тетради правом верхнем углу + номер страницы внизу по центру; перенос строки на
новый лист только по её границе; превью — первая система, рендерится при «Сохранить» →
`tet-<id>.png`.

**Критерии приёмки:** README + 1 detail-файл, секции по порядку; TODO-маркеры; `(№NN)`;
валидные ссылки.

### Шаг 7 — Зачистка и обновление гавернанса (зависит от шагов 1–6)

1. Удалить `domains/placeholder-domain/` — его собственный баннер предписывает удаление
   при первом реальном домене.
2. Переписать `INDEX.md`: таблица «задача → спека» со всеми 12 новыми файлами, ASCII-граф
   зависимостей (модель → layout → рендер; модель → editing → shell; storage под shell),
   полный список каталогов.
3. Хирургические правки (`edit_file`):
   - `META.md` — раздел «Current Project State» (реальные домены появились; плейсхолдер
     остался только в architecture/) + дерево File Organization;
   - `layers.md` — таблица/заметка соответствия канонических слоёв шести доменам;
   - `data-flow.md` — разобранный пример «вставить ноту» по стадиям 1–5.
4. Проверить, что не осталось битых ссылок (ссылки на placeholder умирают вместе с ним).

**Критерии приёмки:** placeholder-domain удалён; INDEX перечисляет каждый файл спеков,
битых ссылок нет; дерево META соответствует диску; layers/data-flow обновлены с
сохранением формата; чек-лист валидации vibespec-create проходит полностью.

## Итог

13 новых файлов спеков (6 README-доменов + 7 detail), 1 удалённый каталог, 3 обновлённых
гавернанс-файла. Спек-система перестаёт быть «пустой»: первый код (этап 1–2 дорожной
карты) ложится в готовые домены вместо placeholder'ов.
